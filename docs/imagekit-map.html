CHALLA iOS · Core · 이슈 #25

CHALLAImageKit — 이미지 로딩 파이프라인 도해

원격 사진 한 장이 URL에서 화면의 UIImage가 되기까지: 조회 순서, 타입 변환, 캐시 삭제 정책, 그리고 테스트 43개가 각각 증명하는 것.

구성 요소에 마우스를 올리면(모바일은 터치) 그 계층이 답하는 경로만 강조됩니다 — 메모리 캐시 = 가장 싼 경로, 디스크 캐시 = 재실행 후 첫 조회, 네트워크 = 처음 보는 이미지.

1

기초 개념 — pt · px · 다운샘플링

이 모듈의 모든 숫자가 딛고 서 있는 개념 넷. 아는 내용이면 건너뛰어도 된다.

pt (포인트) — 논리 단위

레이아웃이 쓰는 단위. "셀 폭 120pt"는 기기와 무관한 설계상의 크기다. SwiftUI의 frame, CGSize가 전부 pt.

px (픽셀) — 물리 단위

화면의 실제 발광점. 같은 120pt라도 @2x 기기는 240px, @3x 기기는 360px로 그린다. 환산식: px = pt × scale. 이미지가 실제로 채워야 하는 건 px 쪽이다.

비트맵 — 펼쳐진 픽셀

파일(JPEG/HEIC)은 압축본이고, 화면에 그리려면 픽셀 격자로 펼쳐야(디코딩) 한다. 펼친 크기는 가로px × 세로px × 4바이트(픽셀당 RGBA) — 파일 용량과 무관하다.

다운샘플링 — 작게 "디코딩"

원본을 다 펼친 뒤 줄이는 게 아니라, 디코딩 단계에서부터 타깃 px 크기로만 펼치는 것. 원본 크기의 비트맵이 메모리에 생기는 순간 자체가 없다.

4000×3000 사진 한 장을 120pt 셀(@3x = 360px)에 띄울 때

전부 펼치면(UIImage(data:))   4000 × 3000 × 4 = 48,000,000바이트 ≈ 45.8MB
셀에 필요한 만큼만(다운샘플)     360 ×  360 × 4 =    518,400바이트 ≈ 0.5MB  (약 90분의 1)

pt → px 환산에서 소수가 나오면 올림(ceil)한다 — 레이아웃 나눗셈으로 119.666pt 같은 값이 흔한데, 내림하면 뷰보다 1px 모자란 비트맵을 늘려 그리게 되어 흐려진다. 이 올림 규칙을 다운샘플러(ImageDownsampler)와 캐시 키(PixelSize)가 공유해야 "만든 크기"와 "찾는 크기"가 어긋나지 않는다.

2

구성 요소 지도

동시성 타입 선택 기준 — 이미 스레드 안전한 것을 감싸면 class, 여러 단계짜리 가변 작업을 스스로 지켜야 하면 actor, 상태가 없으면 struct.

ImageLoaderactor
전체 오케스트레이터. 메모리 → 디스크 → 네트워크 순서로 해결하고, 진행 중 작업 맵(inFlight)으로 같은 키 요청을 병합한다.
MemoryImageCachefinal class
NSCache 래핑. NSCache가 자체로 스레드 안전해서 actor가 필요 없다. cost(바이트) 상한 기반.
DiskImageCacheactor
파일 저장 + 용량 합산 + LRU 삭제가 여러 단계로 이어지는 작업이라 직렬화가 필요하다. 파일명은 키의 SHA256.
ImageDownsamplerstruct
ImageIO 썸네일 디코딩으로 타깃 픽셀만큼만 디코딩. 상태 없는 동기 CPU 작업 — 실행 위치는 호출부 책임.
ImageDataEncoderstruct
다운샘플된 CGImage를 HEIC 바이트로 재인코딩(디스크 저장용). 포맷 정책 교체 지점.
ImageCacheKey · PixelSizestruct
PixelSize는 pt·scale을 ceil(pt × scale) 픽셀로 환산해 보관 — 캐시 키의 크기 성분이자 다운샘플 타깃. ImageCacheKey(URL + PixelSize)는 세 곳의 키다: 로더의 inFlight 맵(중복 제거), 메모리 캐시의 NSCache 키(상자로 감싸서), 디스크 캐시의 파일명(SHA256).
ImageDataFetchingprotocol
네트워크 주입 지점. 기본 구현 URLSessionImageDataFetcher는 URLCache를 끈 세션 사용(이중 저장 방지). 테스트는 목으로 대체.
ImageCacheConfigurationstruct
용량·경로 설정. 기본값: 메모리 100MB · 디스크 500MB · Caches/CHALLAImageCache.

3

로더 파이프라인

시나리오를 누르면 그 경우에 실행되는 단계만 밝게 표시됩니다. 각 단계를 누르면 상세가 펼쳐집니다.

시나리오를 선택하지 않으면 전체 단계가 표시됩니다.

0
캐시 키 생성(URL, pt, scale) → ImageCacheKey여기서 반환

PixelSize(pointSize:scale:)가 ceil(pt × scale)로 타깃 픽셀을 확정하고, URL과 묶어 키가 된다. 같은 URL이라도 표시 크기가 다르면 다른 키 — 그리드 셀용과 상세 화면용은 별개 항목으로 캐시된다.

올림(ceil)인 이유: 내림하면 뷰보다 1px 모자란 비트맵을 늘려 그리게 되어 전체가 미세하게 흐려진다. 다운샘플러도 같은 식을 쓰므로 만드는 쪽·찾는 쪽의 키가 항상 일치한다.

1
메모리 조회NSCache · 로더 내부 추가 대기 없음여기서 반환

히트 디코딩까지 끝난 UIImage가 그대로 나온다 — 파이프라인에서 가장 싼 경로, 즉시 반환.

미스 다음 단계로. NSCache는 cost 상한 초과나 시스템 메모리 압박 시 항목을 자동 방출하므로(순서 비보장), 넣었던 것이 없을 수 있다.

2
중복 제거 — 진행 중 작업 확인inFlight: [ImageCacheKey: Task]기존 작업 결과 공유

같은 키의 다운로드가 이미 진행 중이면 새 작업을 만들지 않고 그 Task의 결과를 await로 같이 기다린다. 같은 셀이 화면에 여러 번 뜨거나 빠른 스크롤로 요청이 겹쳐도 네트워크는 키당 1회.

없으면 새 Task를 등록하고 3단계로. 작업 종료 시 맵 정리는 "내가 등록한 task일 때만" 지운다 — 잠든 사이 removeAll() 후 다른 요청이 같은 키로 새 task를 등록했을 수 있어서다(actor 재진입 가드).

3
디스크 조회DiskImageCache(actor) · SHA256 파일명여기서 반환

히트 파일을 읽고 수정일을 지금으로 갱신한다 — LRU 삭제 순서에서 뒤로 밀린다. 저장된 바이트는 이미 다운샘플된 HEIC라 다운샘플 없이 디코딩만 하면 된다 — Task.detached(utility)에서 디코딩 후 메모리 캐시로 승격하고 반환.

미스 / 디코딩 실패 조용히 네트워크로 폴백한다. 파일이 없거나 손상돼도 에러를 내지 않는다 — OS가 Caches 폴더를 언제든 지울 수 있다는 전제로 짠 코드다.

4
네트워크 다운로드 + 재시도fetchWithRetry · 백오프 1 → 2 → 4초

일시적 전송 실패(타임아웃, 연결 끊김, DNS 실패 등 화이트리스트 7종)만 재시도한다. 목록 밖 오류(잘못된 URL 등)는 재시도해도 소용없으므로 즉시 .networkFailed.

응답 검증 3종을 통과해야 다음 단계로: HTTP 응답인가(invalidResponse) → 2xx인가(httpStatus) → 본문이 비어 있지 않은가(emptyData). 404 같은 HTTP 오류는 서버의 확정 답변이므로 재시도하지 않는다.

취소 정책: 호출자(셀)가 사라져도 공유 다운로드는 죽이지 않고 끝까지 받아 캐시를 채운다. 취소된 호출자에게만 .cancelled를 던진다 — 다음 스크롤에서 같은 이미지가 캐시 히트가 되도록. 전송 계층에서 올라온 URLError(.cancelled)도 .networkFailed가 아닌 .cancelled로 매핑한다.

5
다운샘플 + HEIC 인코딩Task.detached(.utility) — 액터 밖 CPU 작업

CGImageSourceCreateThumbnailAtIndex로 원본 바이트를 타깃 픽셀 크기로만 디코딩한다. 4000×3000 원본을 전부 펼치면 45MB(4000×3000×4바이트)지만, 360×360 셀에 필요한 건 0.5MB — 원본 비트맵은 메모리에 아예 생기지 않는다.

디코딩 시 EXIF 회전을 반영해 세로 사진이 눕지 않게 하고, 같은 클로저에서 HEIC로 재인코딩까지 마친다 (디스크 저장용 — 같은 화질에서 JPEG보다 작다. 인코딩 실패는 encodingFailed. HEIC 경로에서 알파 채널은 손실될 수 있는데, 불투명한 필름 사진 중심이라 v1에서 수용한 결정). 무거운 CPU 작업이라 액터 밖(detached, utility 우선순위)에서 실행해 로더가 다른 요청을 계속 받게 한다.

6
저장 후 반환디스크 store(+LRU 방출) · 메모리 insert(cost)여기서 반환

HEIC 바이트는 디스크에(저장 직후 용량 초과분을 LRU로 방출), UIImage는 cost(bytesPerRow × height)와 함께 메모리에 넣는다. 다음 요청부터는 1단계에서 끝난다.

저장이 두 캐시에 각각인 이유 — "디스크에만 넣고 메모리는 승격으로 채우면 되지 않나" 싶지만, 디스크가 가진 건 HEIC 압축 바이트라 그 경로로 올리려면 방금 만든 이미지를 다시 디코딩해야 한다. 지금 손에 있는 UIImage를 바로 메모리에 넣으면 그 비용이 0이다. 승격 경로는 "앱 재실행 뒤 디스크에서 처음 꺼낼 때"를 위한 것이다.

5

cost — 메모리 캐시가 용량을 세는 단위

화면 표시에 쓰는 값이 아니다. NSCache에게 "이 이미지가 메모리를 이만큼 차지한다"를 알려주는 관리용 숫자다.

어떻게 계산하나

let cost = cgImage.bytesPerRow * cgImage.height

한 줄의 픽셀 데이터:  1,200바이트   (bytesPerRow)
이미지 높이:            300줄      (height)
cost = 1,200 × 300 = 360,000바이트  ← 디코딩된 상태의 대략적인 메모리 크기

디스크의 파일 용량과는 전혀 다른 값이다. 같은 이미지라도:

디스크의 HEIC 파일         50KB   (압축된 크기 — DiskImageCache가 세는 값)
디코딩 후 메모리 비트맵    360KB   (펼쳐진 픽셀 크기 — NSCache가 세는 값 = cost)

어디로 흘러가나

① 상한 설정 — 로더 생성 시 한 번
   MemoryImageCache(costLimit: 100MB) → 내부에서 cache.totalCostLimit = 100MB

② 비용 신고 — 메모리 캐시에 이미지가 들어가는 두 시점마다
   (네트워크 다운로드 직후 저장할 때 · 디스크 히트를 메모리로 승격할 때)
   memory.insert(image, for: key, cost: 360_000)
   → cache.setObject(image, forKey: box, cost: 360_000)

③ 합산 — 넣고 뺄 때마다 NSCache가 자동으로
   이미지 A 10MB + B 15MB + C 20MB = 총 45MB

④ 자동 방출 — 합계가 totalCostLimit을 넘었을 때 + 시스템 메모리 압박 시
   (무엇을 언제 지울지는 NSCache 재량 — 상한은 엄격한 보장이 아니라 관리 힌트)

왜 ProcessedImage · CachedImage가 cost를 담아 오나

CGImage는 액터 밖 Task.detached 클로저 안에서만 존재한다. cost의 재료(bytesPerRow, height)가 그 안에 있으니 만든 자리에서 바로 계산해, 결과 구조체에 화면용·저장용 값과 함께 묶어 액터로 돌려보낸다:

네트워크 경로 — 파이프라인 5단계(다운샘플 직후)에서 계산
              ProcessedImage(image, encodedData, cost)
                              │        │           └ memory.insert의 비용 신고
                              │        └ 디스크 저장 (HEIC 바이트)
                              └ 화면 반환 + 메모리 캐시

디스크 경로   — 파이프라인 3단계(디스크 히트를 디코딩한 직후)에서 계산
              CachedImage(image, cost)
              — 디스크의 HEIC를 다시 펼쳤으니 메모리 비용도 다시 계산해서 승격에 사용

정리 — cost는 나중에 꺼내 쓰는 값이 아니라, 만들자마자 memory.insert로 넘겨 NSCache의 용량 관리(합산 → 상한 초과 시 방출)에 바로 쓰이는 값이다. 우리가 정하는 건 상한(memoryCostLimitBytes, 기본 100MB)과 이미지별 신고값(cost)까지고, 방출 시점·순서는 NSCache가 정한다.

6

캐시는 언제, 누가 비우나

지우는 주체가 넷이고 조건이 전부 다르다. 어느 층이 비어 있어도 파이프라인이 다음 층으로 넘어가므로 기능은 항상 동작한다.

메모리 — NSCache 자동 방출

cost 총합이 상한(기본 100MB)을 넘거나 시스템 메모리 압박 시 NSCache가 스스로 방출한다. 방출 순서는 비보장. 앱 생명주기 알림(UIApplication) 구독 없이 이 자동 동작만으로 충족한다 — Core 모듈이 앱 실행 상태를 관찰하지 않게 유지하고, 강제 정리는 상위가 removeAll()로 한다.

디스크 — 자체 LRU

저장할 때마다 총 용량을 재고, 상한(기본 500MB) 초과분을 수정일이 오래된 파일부터 삭제한다. 조회 적중 시 수정일을 갱신하므로 자주 보는 사진은 뒤로 밀린다. 평상시 용량 관리는 전적으로 이 알고리즘 몫.

OS — Caches 폴더 청소

기기 저장 공간이 부족하면 iOS가 Caches/ 파일을 지울 수 있다. 우리가 디스크 캐시를 일부러 여기에 둔 이유다 — iOS 파일 배치 규칙이 "지워지면 안 되는 사용자 데이터는 Documents/, 다시 만들 수 있는 파일은 Caches/"인데, 이미지 캐시는 재다운로드하면 그만이라 후자다. Documents/에 두면 지워지지도 않고 설정 → 저장 공간에서 앱 용량으로만 쌓인다. OS 청소는 시점 보장이 없어 관리 수단으로 쓰지 않고, 언제 지워져도 동작하는 것(미스 처리 → 재다운로드)으로 견딘다.

상위 계층 — removeAll()

로그아웃 등에서 상위가 명시적으로 호출한다. 진행 중 다운로드를 전부 취소하고 메모리·디스크를 모두 비운다. 유일하게 "지금 당장, 전부"를 보장하는 경로.
